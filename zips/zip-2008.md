# Terminology

The key words "MUST" and "MAY" in this document are to be interpreted as described
in BCP 14 [^BCP14] when, and only when, they appear in all capitals.

The term `NU7ActivationHeight` is to be interpreted as defined in ZIP 218
[^zip-0218].


# Abstract

This ZIP updates the address list for the `FS_FPF_ZCG_H3` funding stream,
reflecting operational changes by the recipient.


# Motivation

The recipient of the `FS_FPF_ZCG_H3` funding stream notified the ZIP Editors
that there was a need to receive the funding stream into a new address. This
change can only happen at network upgrade boundaries, because the funding
stream recipient addresses are part of the consensus rules.


# Requirements

- Funding stream outputs for `FS_FPF_ZCG_H3` start being received at the new
  address shortly after the NU activates that deploys this ZIP.


# Specification

## Changes to ZIP 207

In "Funding streams" [^zip-0207], after the paragraph starting with:

> As of `Revision 1`_, each recipient identifier MUST be...

add:

> As of `Revision 2`_, each recipient identifier MUST be either the string encoding
> of a transparent P2PKH or P2SH address or of a Sapling address (as specified in
> `[#protocol-transparentaddrencoding]_` or `[#protocol-saplingpaymentaddrencoding]_`)
> or the identifier $\mathsf{DEFERRED\_POOL}$.

In "Consensus rules" [^zip-0207], at the end of rule 4, add:

> As of `Revision 2`_, the "prescribed way" to pay a transparent P2PKH address
> is to use ``OP_DUP OP_HASH160 <keyHash> OP_EQUALVERIFY OP_CHECKSIG`` as the
> output's ``scriptPubKey``, where ``<keyHash>`` is the direct push of the
> 20-byte public-key hash decoded from the recipient's Base58Check address. No
> other script encoding satisfies this funding-stream payment rule.

## Changes to the Zcash Protocol Specification

In § 7.10 'Payment of Funding Streams, Deferred Lockbox, and Lockbox Disbursement',
from NU7 activation, extend the permitted funding-stream recipient types to
include transparent P2PKH addresses. Add the P2PKH prescribed payment rule above
alongside the existing P2SH and shielded payment rules. The amount and distinct
output requirements are unchanged.

## Activation constraint

The Mainnet NU7 activation height MUST be chosen such that $0 \leq N < 36$.
This ensures that at least one remaining funding period selects the new address.
With the current funding schedule and the multiple-of-three activation constraint,
the latest permitted Mainnet activation height is 4,371,399.

## Consensus node implementor note

Once a mainnet activation height has been specified in ZIP 259 [^zip-0259],
implementations MAY use a fixed array of addresses in the correct sequence,
instead of dynamically calculating `N`.


# Rationale

The ZIP modifies the existing address list such that the new address will start
being used from the first funding period that begins after NU7 activation. This
means that depending on the precise value of `NU7ActivationHeight`, the updated
address might begin usage anywhere from "immediately" to "about a month" after
activation. This approach was chosen for its simplicity, given the lack of time
before NU7 activation. An alternative approach that instead changed the address
at NU activation would require more significant changes to ZIP 214 [^zip-0214]
(and possibly ZIP 207 [^zip-0207]).


# Deployment

This ZIP is proposed to be deployed with NU7 [^zip-0259].
