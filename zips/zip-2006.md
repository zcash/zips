# Abstract

NU6.3 [^zip-0258] specifies two restrictions intended to limit economic activity
within the *Orchard pool*:

* Value can leave the *Orchard pool* but cannot enter it.
* Each *Orchard-pool* Action must send its output to the same expanded receiver
  as the note that it spends.

So the *Orchard pool* can still be spent from, including across the turnstile
into the *Ironwood pool*, but cannot be used to transfer value to an address
whose spending key the sender does not hold.

This ZIP specifies the `enableCrossAddress` flag that expresses the second
restriction; the corresponding condition in the Action statement; and the
consensus rules that enforce both restrictions for the *Orchard pool*.


# Motivation

The Orchard Action circuit deployed before NU6.2 had a soundness vulnerability
that could have allowed value to be created in the *Orchard pool*. [^zip-0257]
NU6.3 introduces the *Ironwood pool*, which uses the Orchard protocol with a
corrected circuit. Value moves from the *Orchard pool* into it subject to the
"turnstile" checks on chain value pool balances specified in ZIP 209 [^zip-0209].

For those checks to give the desired balance integrity assurances, newly created
shielded value has to be directed into the *Ironwood pool*, and value in the
*Orchard pool* should only be able to leave it. If users could still pay each
other within the *Orchard pool*, it would remain a working payment pool, and any
value created through the vulnerability could circulate in it without ever being
checked at the turnstile. Disallowing new value from entering the *Orchard pool*,
and payments between users within it, prevents that, while still letting each
holder move their own funds out. It does not prevent users from rebalancing
note values within the *Orchard pool* in order to reduce the information revealed
when migrating those funds to the *Ironwood pool*, as specified in ZIP 318 [^zip-0318].


# Requirements

* After NU6.3 activation, no transaction can increase the *Orchard pool*'s chain
  value pool balance.
* After NU6.3 activation, an *Orchard-pool* Action cannot transfer value to an
  address other than that of the note it spends.
* Holders of *Orchard-pool* notes can still spend them, including into the
  *Ironwood pool*, through the turnstile.
* Holders of *Orchard-pool* notes can rebalance their values within that pool.
* The restriction is enforced for every *Orchard-pool* Action mined after NU6.3
  activation, whatever the version of the transaction that contains it.
* Signers that treat bit 2 of `flagsOrchard` as a reserved zero bit can still
  produce valid *Orchard-pool* spends.


# Specification

## The `enableCrossAddress` flag

Each Action has a flag
$\mathsf{enableCrossAddress} \;{\small ⦂}\; \mathbb{B}$, which is set in
order to allow the expanded receiver of the Action's output note to differ from
the expanded receiver of its input note. The value of
$\mathsf{enableCrossAddress}$ is the same for all Actions of a bundle, and is
encoded once per bundle in bit 2 of its flags byte:

* In the `flagsIronwood` field of a version 6 transaction, bit 2 encodes
  `enableCrossAddress` for the *Ironwood-pool* Actions. [^zip-0229]
* In the `flagsOrchard` field, bit 2 MUST be 0, independent of the transaction
  version. In a version 5 transaction it is still reserved and MUST be 0. In a
  version 6 transaction it encodes `enableCrossAddress`, and MUST be 0.

For blocks before NU6.3 activation, cross-address transfers are always
permitted: $\mathsf{enableCrossAddress}$ is taken to be $1$ for every Action.
From NU6.3 activation, $\mathsf{enableCrossAddress}$ is bit 2 of the flags byte
for each pool, so it is $0$ for every *Orchard-pool* Action.

## Action statement

For a given Orchard-protocol Action description, let
$\mathsf{disableCrossAddress} = 1 - \mathsf{enableCrossAddress}$.

From NU6.3 activation, the Action statement gains a primary input
$\mathsf{disableCrossAddress} \;{\small ⦂}\; \mathbb{B}$, after
$\mathsf{enableOutputs}$, and the following condition:

> **Cross-address restriction**: $\mathsf{disableCrossAddress} = 0$, or
> $\mathsf{g_d^{old}} = \mathsf{g_d^{new}}$ and
> $\mathsf{pk_d^{old}} = \mathsf{pk_d^{new}}$.

The auxiliary input of the Action statement already includes the spent note's
expanded receiver $(\mathsf{g_d^{old}}, \mathsf{pk_d^{old}})$ and the output
note's expanded receiver $(\mathsf{g_d^{new}}, \mathsf{pk_d^{new}})$.

A single circuit, and a single verifying key identified as
`OrchardCircuitVersion::PostNU6_3`, are used for the Actions of both the
*Orchard pool* and the *Ironwood pool* from NU6.3 activation. The pools differ
in the consensus restrictions on the value of $\mathsf{enableCrossAddress}$,
not in the circuit.

## Consensus rules

The following consensus rules apply from NU6.3 activation to every transaction,
whatever its version:

* The verifying key for the proof of an Action description MUST be the one
  identified as `OrchardCircuitVersion::PostNU6_3`, and the proof MUST be valid
  for the primary input that includes $\mathsf{disableCrossAddress}$.
* A coinbase transaction MUST NOT contain any *Orchard-pool* Actions.
* $\mathsf{v^{balanceOrchard}}$, encoded as the `valueBalanceOrchard` field
  when it is present, MUST be nonnegative. That is, a transaction can take value
  from the *Orchard pool*, but MUST NOT add value to it.

Together with the rule that bit 2 of `flagsOrchard` is 0, these ensure that
after NU6.3 activation no value enters the *Orchard pool*, and every
*Orchard-pool* Action sends its output to the expanded receiver of the note that
it spends.

## Requirements on wallets

When an Action with $\mathsf{enableCrossAddress} = 0$ needs a dummy output note,
that note MUST be sent to the expanded receiver of the Action's spent note
(which may itself be a dummy note), rather than to a random address. Likewise,
a dummy spent note paired with an output note that is not a dummy MUST be at the
expanded receiver of the output note.

ZIP 326 specifies how wallets spend from, and rebalance notes within, the
*Orchard pool* after NU6.3 activation. [^zip-0326-orchard] In particular, an
Action that creates an output note carrying value pairs it with a dummy spent
note at the same expanded receiver, and the dummy output note of an Action that
spends a real note has a random note ciphertext.

## Changes to the Protocol Specification

This section is written as a set of changes relative to version 2026.7.0 of the
protocol specification [^protocol-base]. They are applied in version 2026.8.0.
[^protocol-updated] Each change applies from NU6.3 activation, and is marked as
such in the specification.

### § 4.6 ‘Action Descriptions’

Add:

> Let $\mathsf{pool} \;{\small ⦂}\; \{\mathsf{OrchardPool}, \mathsf{IronwoodPool}\}$
> be the pool of this Action description.
>
> Define an expanded receiver as in ZIP 2006, i.e.
> $(\mathsf{g_d}, \mathsf{pk_d})$ for a shielded payment address.

Add $\mathsf{enableCrossAddress}$ to the components of an Action description,
after $\mathsf{enableOutputs}$, with the description:

> $\mathsf{enableCrossAddress} \;{\small ⦂}\; \mathbb{B}$ is a flag that is set
> in order to enable the expanded receiver of the output note to be different
> from the expanded receiver of the input note in this Action.

In the description of the proof, and in the consensus rule requiring it to be
valid, append $\mathsf{disableCrossAddress}$ to the primary input, where
$\mathsf{disableCrossAddress} = 1 - \mathsf{enableCrossAddress}$.

In the note on components that are encoded once for each pool, add
$\mathsf{enableCrossAddress}$ to the components listed.

Add the consensus rule:

> [NU6.3 onward] $\mathsf{vk}$ MUST be the verifying key identified by
> `OrchardCircuitVersion::PostNU6_3`.

### § 4.8.3 ‘Dummy Notes (Orchard)’

After the steps that construct the spend-related fields for a dummy
*Orchard-pool* input note, add:

> [NU6.3 onward] If $\mathsf{enableCrossAddress} = 0$ for the Action, and its
> output note is not a dummy note, then the first two steps are replaced:
> $(\mathsf{ak}, \mathsf{nk}, \mathsf{rivk})$ and $(\mathsf{d}, \mathsf{pk_d})$
> are instead the full viewing key and diversified payment address of the output
> note's recipient, and the spend authorization signature for the Action is made
> with the corresponding spend authorizing key.

After the paragraph saying that a dummy *Orchard-pool* output note is sent to a
random shielded payment address, add:

> [NU6.3 onward] If $\mathsf{enableCrossAddress} = 0$ for the Action, the dummy
> output note is instead sent to the expanded receiver of the Action's spent
> note. If the spent note is not a dummy note, the transmitted note ciphertext
> of the dummy output note is filled with random bytes rather than being an
> encryption of its note plaintext. [^zip-0326-orchard]

### § 4.18.4 ‘Action Statement (Orchard)’

Append to the primary input:

> [NU6.3 onward] $\mathsf{disableCrossAddress} \;{\small ⦂}\; \mathbb{B}$

After the "Enable output flag" condition, add:

> **Cross-address restriction** [NU6.3 onward]:
> $\mathsf{disableCrossAddress} = 0$, or
> $\mathsf{g_d^{old}} = \mathsf{g_d^{new}}$ and
> $\mathsf{pk_d^{old}} = \mathsf{pk_d^{new}}$.

### § 7.1.2 ‘Transaction Consensus Rules’

Add:

> [NU6.3 onward] A coinbase transaction MUST NOT have any *Orchard-pool* Action
> descriptions.
>
> [NU6.3 onward] $\mathsf{v^{balanceOrchard}}$ MUST be nonnegative.

After the rule that the reserved bits $2..7$ of the `flagsOrchard` field MUST be
zero, add:

> [NU6.3 onward] In a version 6 transaction, bit 2 of `flagsOrchard` encodes
> $\mathsf{enableCrossAddress}$ for the *Orchard-pool* Actions; it is covered by
> the preceding rule, and so is $0$.

# Rationale

## Polarity of the flag

The flag is encoded in the enabled sense: bit 2 is 1 when cross-address
transfers are enabled, the normal case for the *Ironwood pool*. With the
opposite sense, a post-NU6.3 *Orchard-pool* spend would have to set bit 2 to 1.
Signers that treat bit 2 as a reserved zero bit, such as hardware wallet
firmware that has not been upgraded, would then be unable to produce valid
*Orchard-pool* spends. In the enabled sense, the restricted state is bit 2 = 0,
which is exactly what such signers already produce.

Within the circuit, the primary input is the negated value
$\mathsf{disableCrossAddress} = 1 - \mathsf{enableCrossAddress}$. Then a
condition of the form
<span style="white-space: nowrap">"$\mathsf{disableCrossAddress} = 0$ or $a = b$"</span>
is enforced directly by the constraint
$\mathsf{disableCrossAddress} \cdot (a - b) = 0$.

## One circuit for both pools

The *Orchard pool* and the *Ironwood pool* use the same circuit and verifying
key from NU6.3 activation. They are distinguished by their bundles, note
commitment trees, nullifier sets, and chain value pools, and by the value of
$\mathsf{enableCrossAddress}$. This avoids a separate circuit for the restricted
pool. It also leaves open the option of enforcing similar restrictions on the
*Ironwood pool* in future, should there be a reason to. This intentionally
mirrors the design of the `enableSpends` and `enableOutputs` flags.

## Comparing both coordinates

In the circuit, the points of the expanded receivers are witnessed in affine
coordinates, and the condition is enforced coordinate-wise: for each
$\mathsf{P} \in \{\mathsf{g_d}, \mathsf{pk_d}\}$ and each coordinate
$\mathsf{c} \in \{x, y\}$,
$\mathsf{disableCrossAddress} \cdot (\mathsf{c}(\mathsf{P^{old}}) - \mathsf{c}(\mathsf{P^{new}})) = 0$.
Both coordinates are needed.

## Restricting value as well as addresses

The cross-address restriction alone does not stop new value from entering the
*Orchard pool*, since an Action can send value to its own spent note's address.
The rule that $\mathsf{v^{balanceOrchard}}$ is nonnegative, and the rule that
coinbase transactions have no *Orchard-pool* Actions, close that path.
