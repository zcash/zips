Abstract

This ZIP proposes an encoding for v7 Zcash transactions that reduces the impact of future transaction format changes on wallets and other clients. Previous format changes required clients to update their parsers even when they did not use newly introduced protocol features.

The format defines typecode-length-value encodings for protocol bundles and a value pool delta map describing each bundle's effect on the transparent transaction value pool. The entries of this map serve the same purpose as the Sapling and Orchard value balance fields have done in the past. Effecting data and authorizing data are encoded separately, allowing authorizing data to be pruned without removing the transaction's effects.

Clients can parse the common transaction envelope and enumerate public value flows without understanding every bundle type or variant. Computing the transaction identifier additionally requires a supplied digest for each unsupported effecting bundle. This does not eliminate the need to update wallets for consensus changes that alter how they must construct or interpret transactions.

Future additive bundle introductions can avoid making wallets' support for unused features distinguishable on-chain, reducing the need for further transaction-format changes and their associated privacy leakage.

Motivation

In the past, Zcash network upgrades that changed the transaction format have resulted in substantial disruption for wallets and other third-party clients in the Zcash ecosystem. In order to continue functioning after a network upgrade, clients were required to upgrade their Zcash transaction parsers to read the new format, even if the context in which those parsers were being used didn't need or couldn't make use of newly added transaction data. An example of this is that transparent-only wallets were forced to update their parsers to understand the Sapling and Orchard parts of transactions, even if they would never read or act upon those parts. This has led on occasion to significant problems in the Zcash ecosystem, including situations where funds have been locked and rendered unspendable from transparent-only wallets.

For some kinds of changes to consensus features, it's imperative that every wallet be aware of and be adapted to those changes, and in those cases making a major (breaking) transaction version update as we've done in the past is appropriate. For many new features, however, it is possible for a wallet to continue functioning correctly without having to fully understand a transaction using that feature.

For example, if TZEs were to be added to the protocol, it would be possible for wallets to continue operating with transparent/Sapling/Orchard functionality, ignoring TZE parts. There is substantial precedent for this sort of behavior; transparent-only hardware wallets are currently still important in the Zcash ecosystem, and many wallets didn't begin interacting with Orchard transaction parts until quite a while after Orchard activation.

After this change to transaction encoding, wallets and other third parties will not be required to update their transaction parsers in advance of a network upgrade for the introduction of many (and perhaps most) types of new protocol features. This will enable the Zcash ecosystem to make smaller and more incremental network upgrades without breaking existing wallets.

Privacy Implications

This change alters the encoding of transactions, but does not alter the information content of the transaction. As such, the only implication of this change is that the use of this transaction format acts as a 1-bit distinguisher that reveals that the wallet that generated the transaction has been updated to be aware of the new format. This information leakage is unavoidable for any transaction format change.

In the future, this change may reduce the amount of information leakage, since transactions created using the proposed TLV format will include bundles only for those protocols for which the transaction modifies chain state. For example, if this transaction format change is deployed in NU8 and a hypothetical NU9 defines a bundle type for TZE components, it will not be possible for a chain observer to distinguish whether or not the wallet that produced an Orchard-only transaction is one that has been updated to understand the TZE component. Under prior practices for changing the transaction format, this would have been distinguishable.

In summary, this proposal provides a net improvement in user privacy in addition to its other benefits.

Requirements

  • The transaction format can be parsed without any knowledge of any Zcash payment protocols.
  • Movement of value into and out of the transparent transaction value pool can be understood with only partial knowledge of the Zcash payment protocols.
  • The information content of transactions should not change as part of this ZIP. Other ZIPs activated along with this ZIP may however make use of it in introducing such changes.
  • It must be possible for wallets to parse any transaction that is valid within a version group that it understands, even if it doesn't have handling for or understand all of the bundle types that are valid for that version group. In such a situation, however, such a wallet must still be able to accurately describe any transparent movement of funds effected by the transaction, and alert the user if the transaction contains bundles that it does not understand.
  • It must be possible for a wallet to correctly construct and sign transactions for a given transaction version group that it understands, even if it doesn't have handling for or understand all of the bundle types that are valid for transactions in that version group.

Non-requirements

  • It is not required to eliminate the need to update wallets for consensus changes that alter how they must construct or interpret transactions.

Specification

Protocol Bundles

This ZIP refines and codifies the concept of "protocol bundles" that emerged from the implementation of the ZIP 225 18 transaction format. It makes bundles first-class objects and defines a registry of bundle type and variant identifiers. Within the period that a given transaction format version is used on the Zcash network, the semantics of the bundle associated with a given (bundleType, bundleVariant) pair are fixed.

A protocol bundle is a self-contained component of a transaction that implements a specific piece of protocol functionality. Each bundle is identified by a (bundleType, bundleVariant) pair, where:

  • The bundle type identifies the protocol or value pool that the bundle operates on (e.g., Transparent, Sapling, Orchard).
  • The bundle variant identifies a specific variant of that protocol. New variants of an existing bundle type may be introduced by subsequent ZIPs to evolve a protocol's functionality while preserving the association with the same value pool.

A transaction MUST NOT contain more than one variant of any given bundle type. This constraint is enforced by the map structure of the transaction encoding: the maps mValuePoolDeltas, mEffectBundles, and mAuthBundles are each keyed by bundleType alone, and the parsing rules require the same bundleVariant for a given bundleType across all three maps.

Each bundle type/variant pair defines:

  • What effecting data the bundle contains — the data that determines what state changes the bundle produces (e.g., which notes are spent, which outputs are created, which transparent UTXOs are consumed or produced).
  • What authorizing data the bundle contains — the proofs and signatures that authorize the state changes specified by the effecting data.
  • How the bundle affects the transparent transaction value pool — whether the bundle adds value to, removes value from, or has no effect on this ephemeral pool that balances value flows within a transaction.

Rationale for Effecting Data and Authorizing Data

Click to show/hide

The separation of effecting data from authorizing data serves several purposes:

  1. Transaction identifier stability: The transaction identifier (txid) is computed only from the effecting data. This means that the txid is determined by what the transaction does, not by how it is authorized. Third parties cannot change a transaction's identifier by modifying signatures or proofs.
  2. Efficient pruning: Full nodes that have validated a transaction may prune the authorizing data while retaining the effecting data. Since authorizing data appears at the end of the encoded transaction, pruning is simply truncation.
  3. Partial processing: A wallet can parse a transaction's envelope without understanding every bundle type or variant. To compute the transaction identifier, it needs the corresponding bundle_effects_digest for each unsupported effecting bundle, as described in Implications for Wallets; hashing the opaque payload does not in general produce that digest.

The Transparent Transaction Value Pool

The transparent transaction value pool is an ephemeral concept that exists only within the scope of processing a single transaction. It serves as a balancing mechanism through which value flows between bundles.

Each bundle may contribute a value pool delta — a signed value indicating how much the bundle adds to or removes from the transparent transaction value pool. A positive delta means the bundle is adding value to the pool (e.g., a shielded spend releasing value), while a negative delta means the bundle is consuming value from the pool (e.g., a shielded output absorbing value, or a transaction fee).

For a valid transaction, the sum of all value pool deltas MUST equal zero. This ensures that value is neither created nor destroyed — it is only transferred between bundles within the transaction.

This holds for coinbase transactions as well. The part of the block subsidy that the transaction pays out enters the transparent transaction value pool as the value pool delta of the coinbase bundle, and the fees collected from the other transactions in the block enter it as the value pool delta of the fee bundle; the coinbase outputs then consume that value like any other bundle.

Bundle Type Registration

When a ZIP introduces a new bundle type or a new variant of an existing bundle type, it MUST:

  1. Request allocation of a (bundleType, bundleVariant) pair in the registry defined below. The bundleType and bundleVariant are each non-negative integers. If the ZIP introduces a new bundle type, it requests a new bundleType value with bundleVariant 0. If it introduces a new variant of an existing bundle type, it requests a new bundleVariant value for the existing bundleType.
  2. Specify whether entries for this bundle type are permitted in mValuePoolDeltas (the value pool delta map).
  3. Specify whether entries for this bundle type are permitted in mEffectBundles (the effecting data map).
  4. Specify whether entries for this bundle type are permitted in mAuthBundles (the authorizing data map).
  5. If effecting data is permitted, define the encoding of that data.
  6. If authorizing data is permitted, define the encoding of that data.
  7. Define the digest algorithm for the bundle's contribution to the transaction identifier, if effecting data is present.
  8. Define the digest algorithm for the bundle's contribution to the authorizing data commitment, if authorizing data is present.

A bundle type MUST NOT permit entries in mAuthBundles unless it also permits entries in mEffectBundles. That is, authorizing data cannot exist without corresponding effecting data for a given bundle type.

If a bundle's encoding defines a per-element sequence in its authorizing data as corresponding to a per-element sequence in its effecting data, it MUST specify that the two sequences have the same length and that elements at the same index correspond.

Once a (bundleType, bundleVariant) pair is assigned for a given transaction version, its semantics are fixed for the lifetime of that transaction version. A subsequent network upgrade may define a new transaction version that reassigns identifiers or changes bundle semantics, but within a single transaction version, bundle type and variant identifiers have stable, unchanging meanings.

A new variant of an existing bundle type MUST affect the same value pool(s) as the original bundle type. This ensures that a client that does not recognize a particular bundleVariant can still determine which pool(s) are affected by the bundle and inform its user accordingly.

Rationale for non-extensible Common Transaction Fields

Click to show/hide

A transaction contains two kinds of information:

  • Changes enacted on global chain state. These belong in effecting bundles, including changes that move no value (such as the potential key rotation bundle in ZIP 270). Together with the value pool delta and authorizing data maps, these provide extensibility for the kinds of future changes currently envisaged.
  • Constraints on when the state change may be enacted. Pool-specific constraints are encoded within the corresponding effecting or authorizing bundles, while pool-agnostic constraints are encoded within the Common Transaction Fields.

There are no current proposals for pool-agnostic constraints that would require extensible Common Transaction Fields. Making them extensible without a concrete use would also require choosing commitment rules for fields whose semantics are not yet known. The Common Transaction Fields are therefore kept fixed rather than adding speculative flexibility. If future ZIPs require additions or modifications to the Common Transaction Fields, a new transaction version can introduce them while retaining compatibility with this ZIP's bundle registry (by explicitly importing those bundle definitions into its bundle registry).

Parsing Rules

The rules in this section are requirements on the byte encoding of a v7 transaction. A byte stream that violates any of these rules is not a well-formed v7 transaction and MUST be rejected by any parser, regardless of which bundle types the parser understands. Enforcement of these rules is what makes it safe for a wallet to parse, identify, and compute the transaction identifier for a transaction containing bundle types that the wallet does not itself implement.

  • Each of mValuePoolDeltas, mEffectBundles, and mAuthBundles MUST contain at most one entry per bundleType, and the entries MUST be encoded in strictly increasing bundleType order.
  • Every ValuePoolDelta record MUST have a nonzero value field. A ValuePoolDelta record that would have value = 0 MUST be elided from the encoding of mValuePoolDeltas.
  • For each bundleType that appears in any of mValuePoolDeltas, mEffectBundles, or mAuthBundles, all entries for that bundleType across all three maps MUST encode the same bundleVariant. (Together with the uniqueness rule above, this ensures that a transaction uses at most one variant of any given bundle type.)
  • For each bundleType that appears in mAuthBundles, a corresponding entry with the same bundleVariant MUST exist in mEffectBundles.

A wallet that successfully parses a v7 transaction under these rules is guaranteed to be able to compute the transaction identifier (given, for each (bundleType, bundleVariant) pair in mEffectBundles it does not understand, the corresponding 32-byte bundle_effects_digest value as described in Implications for Wallets), and to enumerate the transparent value flows of the transaction at the granularity of bundle types.

Let CoinbaseBundleId, SaplingBundleId, OrchardBundleId, IronwoodBundleId, and FeeBundleId be the identifiers of the coinbase, Sapling, Orchard, Ironwood, and fee bundles, respectively. In v7 transactions, \(\mathsf{CoinbaseBundleId} = 1\kern-0.03em\textsf{,}\) \(\mathsf{SaplingBundleId} = 2\kern-0.03em\textsf{,}\) \(\mathsf{OrchardBundleId} = 3\kern-0.03em\textsf{,}\) \(\mathsf{IronwoodBundleId} = 4\kern-0.03em\textsf{,}\) and \(\mathsf{FeeBundleId} = 5\) as defined in the table above.

Shielded balancing values

The logical Sapling, Orchard, and Ironwood balancing values are signed integers measured in zatoshis, as defined in the 'Balance and Binding Signature' sections of the protocol specification. 8 9 They are obtained from the v7 encoding as follows:

\(\begin{aligned} \mathsf{v}^{\textit{SaplingPoolBalance}} &= \mathsf{mValuePoolDeltas}[\mathsf{SaplingBundleId}] \\ \mathsf{v}^{\textit{OrchardPoolBalance}} &= \mathsf{mValuePoolDeltas}[\mathsf{OrchardBundleId}] \\ \mathsf{v}^{\textit{IronwoodPoolBalance}} &= \mathsf{mValuePoolDeltas}[\mathsf{IronwoodBundleId}] \end{aligned}\)

Each balancing value has the sign convention defined for its pool: a positive value takes net value from the corresponding chain value pool and adds it to the transparent transaction value pool; a negative value does the reverse.

Coinbase accounting values

For a v7 coinbase transaction, the transparent outputs used in the total output value definition in § 7.1.2 'Transaction Consensus Rules' are the entries in tx_out of its transparent bundle, or the empty sequence if that bundle is absent. 11 The shielded balancing values in that definition are obtained as specified above. The coinbase bundle's blockSubsidy and lockboxValue fields equal the protocol-defined block subsidy and \(\mathsf{totalDeferredOutput}(\mathsf{height})\kern-0.03em\textsf{,}\) respectively, as required by the Cross-bundle and chain-context rules.

Transaction inputs and outputs

For variant 0 of the corresponding bundle types, the logical counts and flags used in the protocol specification are obtained from the v7 effecting data as follows:

  • \(\mathtt{tx\_in\_count}\) and \(\mathtt{tx\_out\_count}\) are the transparent bundle's tx_in_count and tx_out_count fields.
  • \(\mathtt{nSpendsSapling}\) and \(\mathtt{nOutputsSapling}\) are the Sapling bundle's nSpendsSapling and nOutputsSapling fields.
  • \(\mathtt{nActionsOrchard}\) and \(\mathtt{nActionsIronwood}\) are the nActionsOrchard field of the Orchard and Ironwood bundles, respectively.
  • \(\mathtt{enableSpendsOrchard}\) and \(\mathtt{enableOutputsOrchard}\) are the enableSpends and enableOutputs bits of the Orchard bundle's flagsOrchard field. \(\mathtt{enableSpendsIronwood}\) and \(\mathtt{enableOutputsIronwood}\) are the corresponding bits of the Ironwood bundle's flagsOrchard field.

Counts are nonnegative integers and flags are bits. If a bundle is absent, its counts and flags are zero.

Changes to the Protocol Specification

Consensus Rules

This ZIP requires the following modifications to the consensus rules in the Zcash Protocol Specification. These rules are additional to the parsing rules above; a transaction that satisfies the parsing rules but violates any of these consensus rules is well-formed but invalid.

Bundle availability

For every (bundleType, bundleVariant) pair appearing in any of mValuePoolDeltas, mEffectBundles, or mAuthBundles, a full validator MUST verify that the pair is registered for v7 and activated for the consensus epoch of the block containing the transaction. A full validator MUST reject a transaction containing an unregistered or unactivated pair. Registration alone does not activate a bundle type or variant.

These consensus checks do not prevent a wallet from parsing an unsupported bundle type or variant opaquely under Parsing Rules.

Bundle-local rules

The following rules constrain the contents of individual bundles. Full validators MUST enforce every applicable rule. A wallet only needs to enforce a given rule in this subsection if it understands the bundle type and variant that the rule applies to.

  • A bundle type MUST NOT appear in any map for which the corresponding column of the v7 Transaction Bundle Type Registry is marked ❌, and MUST NOT appear in any map at all if its row in the registry is marked as Reserved.
  • Each entry in mValuePoolDeltas for variant 0 of the transparent, coinbase, Sapling, Orchard, or Ironwood bundle MUST have a corresponding entry in mEffectBundles.
  • If a transparent effecting bundle has tx_in_count > 0, a corresponding entry in mAuthBundles MUST be present.
  • For each TransparentInputAuth whose sighashInfo specifies sighash variant 0, the hash_type byte of every nonempty signature supplied to OP_CHECKSIG, OP_CHECKSIGVERIFY, OP_CHECKMULTISIG, or OP_CHECKMULTISIGVERIFY when validating that input MUST be SIGHASH_ALL (0x01).
  • Every Sapling, Orchard, or Ironwood effecting bundle MUST have a corresponding entry in mAuthBundles.
  • A coinbase transaction MUST NOT spend any transparent output. If a transparent bundle is present in a coinbase transaction, its effecting data MUST have tx_in_count = 0.
  • For coinbase transactions, the nSpendsSapling field of the Sapling bundle's effecting data MUST be 0.
  • For coinbase transactions, the enableSpends bit of the flagsOrchard field of every Orchard protocol bundle MUST be 0.
  • In an Orchard bundle, the enableCrossAddress bit of flagsOrchard MUST be 0; that is, transfers into the Orchard pool are restricted to the protocol-level address of the action's spend. 27 The bit is unrestricted in an Ironwood bundle.
Cross-bundle and chain-context rules

The following rules relate the contents of a bundle to the other bundles of its transaction, or to the block that contains it. They MUST be enforced by full validators.

  • For coinbase transactions, the value of \(\mathsf{mValuePoolDeltas}[\mathsf{FeeBundleId}]\) MUST be nonnegative. This represents the total transaction fees collected from all other transactions in the block.
  • For non-coinbase transactions, the value of \(\mathsf{mValuePoolDeltas}[\mathsf{FeeBundleId}]\) MUST be nonpositive. This represents the transaction fee paid by the transaction (expressed as a negative value, since it is removed from the transparent transaction value pool).
  • The fees collected by the coinbase transaction MUST equal the sum of the fees paid by all other transactions in the block, regardless of their transaction formats. For each non-coinbase transaction, its fee is:
    • for a v7 transaction, the negation of \(\mathsf{mValuePoolDeltas}[\mathsf{FeeBundleId}]\kern-0.03em\textsf{;}\)
    • for a pre-v7 transaction, the implicit fee defined in § 3.4 'Transactions and Treestates'. 5

    For a v7 coinbase transaction, its fee bundle value MUST equal this sum. In a block containing only v7 transactions, this is equivalent to requiring the sum of fee bundle values to equal zero.

  • Exactly one transaction in a block MUST be a coinbase transaction, and it MUST be the first transaction in the block.
  • The blockHeight field of the coinbase bundle's effecting data MUST equal the height of the block containing the transaction.
  • The blockSubsidy field of the coinbase bundle's effecting data MUST equal the block subsidy for that block, as defined in § 7.8 'Block Subsidy and Founders' Reward'. 14
  • The lockboxValue field of the coinbase bundle's effecting data MUST equal the total value that the funding streams for that block deposit into the deferred pool, as defined in § 7.10 'Payment of Funding Streams, Deferred Lockbox, and Lockbox Disbursement'. 15
  • The value of \(\mathsf{mValuePoolDeltas}[\mathsf{CoinbaseBundleId}]\) MUST equal the block subsidy less the lockbox deposit and \(\mathsf{NSMFeeContribution}(\mathsf{height})\) for the block containing the transaction.
    \(\mathsf{mValuePoolDeltas}[\mathsf{CoinbaseBundleId}] = \mathsf{blockSubsidy} - \mathsf{lockboxValue} - \mathsf{NSMFeeContribution}(\mathsf{height})\)

    Note that the coinbase value pool delta can be negative.

  • For every transaction, the sum of all value pool delta values MUST equal 0.
    \(\sum_{\mathsf{d} \in \mathsf{mValuePoolDeltas}} \mathsf{d.value} = 0\)

    For v7 transactions, this rule replaces the remaining-value treatment of the transparent transaction value pool in § 3.4 'Transactions and Treestates', including the implicit transaction fee. 5 It does not change the balance or implicit-fee rules for pre-v7 transactions.

Sighash Variants

This ZIP introduces sighash algorithm variants. Where previously each transaction version had a single associated sighash algorithm, going forward it is possible for signers to use any sighash algorithm within the closed set specified for a given transaction version (and made available in consensus via network upgrades).

The sighash variant is encoded as a single byte alongside any associated data that the sighash algorithm variant requires (for deterministically computing the digest):

sighashInfo = [sighashVariant] || associatedData

where associatedData is specific to the bundle it appears in.

The preimage of each signature digest MUST begin with the single-byte sighashVariant, to domain-separate the sighash algorithm variants.

Each bundle type defines the sighash algorithm variants available to its signers, the associatedData that each variant requires, and the digest that a signature using it commits to. Those definitions are given for the bundle types registered by this ZIP in Bundle Definitions.

Variant 0 is the "commit to all effecting data" sighash algorithm. Other variants can define different commitments, including partial commitments across bundles, within a given transaction version. Consensus rules choose the digest algorithm for each signer based on sighashVariant.

Sighash variant information is present alongside each signature in the authorizing data of each bundle.

Digest Algorithms

All digests are personalized BLAKE2b-256 hashes. In cases where no elements are available for hashing (for example, if there are no transparent transaction inputs), a personalized hash of the empty byte array will be used. The personalization string therefore provides domain separation for the hashes of even empty data fields.

The notation BLAKE2b-256(personalization_string, []) is used to refer to hashes constructed in this manner.

Rationale for Variant 0 Commitments
Click to show/hide

The signature digest algorithms previously defined for Zcash have three distinct variants:

  • For v1 and v2 transactions, it followed the Bitcoin convention of using the "hash the transaction" transaction ID digest algorithm while including or omitting information as relevant for the transparent sighash kind.
  • For v3 and v4, a SegWit-style signature hash algorithm used a two-level hash: the outer digest was over commitments to the various different parts of the transaction, while the TxId was unaltered.
  • For v5 and v6, both the TxId and the sighash were tree commitments to the transaction data, with the sighash digest algorithm reusing as many of the inner commitments computed by the TxId digest as possible, but substituting in different digests where signature-relevant data was included or omitted.

All of these variants diverged from the TxId digest because of how the transparent sighash kinds carried over from Bitcoin were defined. Due to a combination of subtleties around the interpretation of the sighash kinds for transparent-only wallets being ported from Bitcoin, and the lack of equivalent information exposed by the shielded actions, the sighash kinds were not adapted to include equivalent logic on the shielded pools. Instead, they always acted as if the shielded components of a transaction were defined with SIGHASH_ALL. As a consequence, the sighash kinds are only effective in transparent-only transactions.

When transaction ID malleability was addressed for v5 transactions in ZIP 244 23, the TxId and sighash digest algorithms were defined such that if you were signing a transaction that contained no transparent information, you just signed the TxId. In addition to being more efficient (as TxIds are usually computed at parsing time and cached), it is clear that this has the property one expects for a signature that is committing to all of the effecting data in a transaction.

For this ZIP's variant 0 digest, we instead commit directly to the TxId in a wrapping digest; the additional signature-specific information that previously was committed in-situ with the effecting data is instead committed beside the TxId. This has the same overall binding property, while improving the efficiency for all shielded signatures as well as SIGHASH_ALL transparent signatures.

This simplicity and efficiency is only possible by dropping support for non SIGHASH_ALL transparent signatures from variant 0. This is justified for several reasons:

  • These transparent signatures can still be created on the network today with v5 or v6 transactions. There are no functionality changes to the transparent signing capabilities in transparent bundle variant 0.
  • The sighash variants introduced in this ZIP provide an equivalent mechanism that does not inherit the semantic baggage of the transparent sighash kinds. A future ZIP could define a sighash variant that provides equivalent functionality, while potentially also expanding it to compatible shielded logic, if demand for such functionality in v7 transactions appears.
    • One difference between the transparent sighash kinds and sighash variants is that a sighash variant is specified at a per-input level, whereas sighash kinds are specified at a per-signature level. The latter can be leveraged in P2SH scripts, albeit being tricky to reason about. However, this difference can be eliminated by either defining the future sighash variant to use the sighash kind bytes that remain embedded into scripts, or by leveraging the associatedData field to store any additional per-signature metadata necessary for the variant.
  • TODO collect data about observed usage of non SIGHASH_ALL sighash kinds.

The additional transaction-wide amount and script commitments preserve the hardware-wallet protections of ZIP 244. 23 The explicit fee defined in ZIP 2002 26 allows a signer to display the committed fee without reconstructing it from input amounts. However, in a transaction with inputs from multiple parties, the signer must also be able to identify which inputs belong to it and their values. Committing to every input's amount and script public key prevents a host from obtaining signatures in separate sessions using inconsistent descriptions of the other inputs, even when those descriptions have the same total input value. All signers commit to these digests, including shielded signers. Their positional correspondence with the transparent inputs binds them to the previous-output references already committed to by the transaction identifier; they need not be adjacent to those references in the hash tree.

Each spend signature's context includes the zero-based index of the input being signed within its bundle's effecting-data array. This binds the signature to that position, even when another input uses the same authorization key. The bundle type and variant distinguish indices belonging to different bundles. Shielded binding signatures have an empty context, distinct from every spend-signature context.

The index is encoded as a fixed two-byte unsigned little-endian integer. The Sapling spend and Orchard protocol action counts are already constrained by consensus to be less than \(2^{16}\kern-0.03em\textsf{.}\) 11 Each transparent input's effecting data occupies 40 bytes, so the 2,000,000-byte block size limit also bounds its index below \(2^{16}\kern-0.03em\textsf{.}\) 4 No additional count limit is needed.

The transaction identifier and the two aggregate input digests can each be computed once per transaction and reused for every signature. The aggregate input digests require the referenced UTXO data, but their computation does not require changing or recomputing the transaction identifier. Implementations can also clone a BLAKE2b state containing the common prefix before appending the signature context, and can reuse the completed digest for multiple signatures authorizing the same input.

BLAKE2b processes 128-byte blocks. With the currently defined one-byte bundle type and variant encodings, the prefix through bundleVariant is 99 bytes. A shielded spend signature has a two-byte context, giving a 101-byte preimage; a shielded binding signature's empty context gives a 99-byte preimage. Both fit in one block. For a transparent input with a script public key of \(L\) bytes, the preimage length is \(149 + \mathsf{CompactSizeLen}(L) + L\) bytes, where \(\mathsf{CompactSizeLen}(L)\) is the length in bytes of the CompactSize encoding of \(L\kern-0.03em\textsf{.}\) A 25-byte P2PKH script gives 175 bytes (47 bytes in the second block); a 23-byte P2SH script gives 173 bytes (45 bytes in the second block). The latter commits to the script public key, not the redeem script. The shared 99-byte prefix does not fill a block: the first block also contains the first 29 bytes of the input's prevout_hash. In general, each of these transparent digests therefore requires two compressions. Inputs spending outputs of the same previous transaction share the first block, allowing its non-final hash state to be reused. Longer scripts can require additional blocks. No transaction-wide input list or bundle effects need to be rehashed for each signature.

Implications for Wallets

Choice of transaction format when sending

When creating a transaction, a wallet SHOULD use the oldest transaction format that is valid at the height at which the transaction is expected to be mined, and that supports every protocol feature the transaction requires. A wallet SHOULD use the v7 transaction format only for transactions that require a feature that no older valid format supports.

Rationale for choice of transaction format

Click to show/hide

The oldest format that can express a transaction is the format that the largest number of receiving wallets can parse. A wallet that has not yet added support for parsing v7 transactions can still detect funds sent to it in a transaction that does not use v7 features.

Support for receiving funds in v7 transactions

Zcash wallets MUST support parsing v7 transactions by the time they are allowed on the network.

Because the v7 transaction format uses a type-length-value encoding for bundles, a wallet is not required to understand the internal encoding of every bundle in order to parse a transaction. However, a wallet that encounters a bundle with an unrecognized bundleType SHOULD alert the user that the transaction contains components it does not understand. A wallet that encounters a bundle with a recognized bundleType but unrecognized bundleVariant SHOULD alert the user that the transaction affects a pool the wallet is aware of, but in a way the wallet does not fully understand.

For each unsupported (bundleType, bundleVariant) pair in mEffectBundles, a wallet needs the corresponding 32-byte bundle_effects_digest value in order to compute the transaction identifier. This includes an unsupported variant of a recognized bundle type. For each such bundle, the wallet uses the supplied digest as T.3c, together with the bundleType and bundleVariant encoded in that transaction's mEffectBundles entry, in T.3: effects_bundles_digest. It computes the digests of supported bundles normally and includes all bundles in transaction order. The header and complete value pool delta map are hashed as specified in T.1 and T.2. Thus access to the unsupported bundles' digests enables the wallet to compute the transaction identifier without interpreting those bundles' internal payloads. How those digests are made available to the wallet is outside the scope of this ZIP.

The supplied digests act as commitments to subtrees that the wallet does not need to compute. If the resulting transaction identifier matches one obtained from a trusted source, this authenticates the effecting data the wallet understands, the header, and the value pool delta map. Without a transaction identifier obtained from a trusted source, computing the correct identifier instead depends on the supplied bundle digests being correct.

Recognizing a bundle type identifies the affected value pool or protocol component, but does not imply that the wallet understands or can operate under the semantics of an unsupported variant.

A wallet MUST NOT construct or sign a transaction containing a bundle type or variant that it does not fully understand.

Transparent Bundle

The transparent bundle's value pool delta in mValuePoolDeltas represents the net value flowing from the transparent inputs to the transparent outputs.

An entry for this bundle in mEffectBundles MUST contain at least one transparent input or output. If both tx_in_count and tx_out_count would be zero, the effecting bundle MUST be omitted instead. An entry in mAuthBundles MUST NOT be present when tx_in_count = 0; the empty authorizing bundle is omitted.

A full validator MUST verify that the value pool delta for bundleType = 0 equals the total value of the transparent inputs minus the total value of the transparent outputs. (The input values are not encoded in the transaction itself; they are obtained from the UTXOs being spent.)

This rule applies to coinbase transactions unchanged. A coinbase transaction has no transparent inputs, so its transparent value pool delta is the negation of the total value of its transparent outputs; the value that those outputs consume is contributed to the transparent transaction value pool by the coinbase bundle and the fee bundle.

Coinbase Bundle

A v7 transaction is a coinbase transaction if and only if mEffectBundles contains an entry with bundleType = 1. The coinbase bundle replaces the otherwise-unspendable transparent input that identified a coinbase transaction in previous transaction versions, and carries the block height that that input was required to encode.

The block subsidy is the whole of the new issuance for the block, which consensus splits between the miner, the funding streams that pay to an address, and the funding streams that deposit into the deferred pool (the "lockbox") 25. Only the part that is not deposited into the lockbox is paid out by this transaction. The full fees collected from the other transactions in the block are contributed separately, as the value pool delta of the fee bundle. The coinbase bundle's value pool delta is the block subsidy less the lockbox deposit and the fee contribution removed from circulation under ZIP 235. 21 It can therefore be positive, zero, or negative. Together with the gross fee delta, it leaves the subsidy less the lockbox deposit plus \(\mathsf{MinerFees}(\mathsf{height})\) available to the output bundles.

The bundle's own effecting data carries blockSubsidy and lockboxValue, so that these amounts are recoverable from the transaction. The fee contribution is derived from the gross fee delta using ZIP 235's calculation.

The coinbase bundle has no authorizing data.

Orchard Protocol Bundles

The Orchard protocol supports two value pools, each with its own note commitment tree, nullifier set, and chain value pool balance. Each is acted upon by its own bundle type: the Orchard bundle, bundleType = 3, acts on the Orchard pool, and the Ironwood bundle, bundleType = 4, acts on the Ironwood pool.

An entry for either bundle type in mEffectBundles MUST contain at least one Action description (nActionsOrchard > 0 or nActionsIronwood > 0). If there would be no Actions for that bundle type, the bundle MUST be omitted instead.

Rationale

Effecting data bundles and authorizing data bundles are stored separately in the transaction format so that the authorizing data may be pruned by straightforward truncation of the encoded representation of the transaction.

Representing the coinbase as a bundle makes the value pool delta balance rule universal. Previously the coinbase transaction was the sole exception: its deltas summed to the negation of the block subsidy rather than to zero, because the subsidy entered the transparent transaction value pool implicitly. With the subsidy carried in the coinbase bundle's value pool delta, every transaction balances to zero, and a wallet can enumerate the value flows of a coinbase transaction using the same rule it applies to any other transaction.

The input and output requirements prevent trivial transactions (with no inputs or outputs). They allow fee-free transfers within a single shielded pool: such a transaction can satisfy both requirements through its spends and outputs even when it has no value pool delta entries. A zero net delta does not imply that no value moves within a pool.

Carrying blockSubsidy and lockboxValue in the effecting data states both components of the issuance in the bundle they belong to, and commits them to the transaction identifier along with the rest of that data. The value pool delta combines their difference with the fee contribution removed from circulation under ZIP 235. Without the explicit fields, a client could see the net delta but not how much was issued or how much went to the lockbox. Deriving them instead is not open to every client: the subsidy is not a function of the block height alone once issuance depends on accumulated chain state, so evaluating the issuance schedule would require a client to track that state. The NSM fee contribution is derivable from the gross fee bundle value already present in the coinbase transaction, so it needs neither an additional coinbase effecting field nor a ZIP 233 entry. ZIP 233 separately provides an explicit bundle for voluntary removal from circulation. 20

The Orchard and Ironwood bundles share one encoding because the Orchard pool and the Ironwood pool are two pools of the same shielded protocol. The action encoding, proving system, authorization, and note encryption are common to both; the pools differ in their note commitment trees, nullifier sets, and chain value pool balances.

Each pool gets its own bundle type rather than a variant of a single type because a variant is required to affect the same value pool(s) as the type it varies, so that a client encountering an unrecognized variant still knows which pools the bundle touches. Two pools therefore cannot share a bundle type, and separate types also keep the two value pool deltas separable, which a client needs in order to report the two chain value pool balances independently.

The Sapling and Orchard protocol anchors are authorizing data rather than effecting data. An anchor selects the note commitment tree state that the bundle's proofs are verified against, which is a property of how the spends are authorized rather than of what the transaction does. Placing it there lets a bundle be re-anchored to a more recent root without changing the transaction identifier, while the proofs still bind to the anchor actually used.

Bundle digests retain the input formats and personalizations of ZIP 229 19 wherever the committed data is unchanged. Effects roots have different personalizations because value balances are committed separately in the value pool delta map. Authorizing digests have different personalizations because signatures include sighashInfo and anchors precede the proofs and signatures. Orchard and Ironwood use distinct personalizations to separate commitments for their respective pools.

The coinbase bundle also gives the coinbase metadata a place of its own. In previous transaction versions that metadata was encoded as the scriptSig of a single transparent input whose previous output reference pointed at nothing, so a coinbase transaction had to be recognized by that unspendable reference, and the block height had to be encoded as a script push. The coinbase bundle encodes the height directly, and its presence identifies the transaction. The coinbaseData limit of 94 bytes holds the encoded size of that field to what the previous encoding spent on the same content. A coinbase scriptSig was limited to 100 bytes, of which the leading push of the block height took 5; of the 95 bytes that remained, the compactSize length prefix of coinbaseData now takes one.

Neither the previous output reference nor the sequence number of the input being replaced is carried over. Both were artifacts of encoding the coinbase metadata as a transparent input: the reference identified no output, and the sequence number had no effect on the validity of a transaction that spends nothing.

The miner signalling fields give miners a structured way to express sentiment on proposals, separate from coinbaseData. Free-form text in coinbaseData would compete for its 94 bytes with pool identifiers and other miner data, and would have to be found by searching for a textual pattern. A signal is a pair of bytes, so a response to a poll with many options stays small. The 16-byte pollDigest binds the signals to one poll document, so a signal code needs to be unique only within that poll. The fields are committed to by coinbase_effects_digest like the rest of the coinbase bundle, so they cannot be altered without changing the transaction identifier. Requiring strictly ascending signal codes gives each set of signals a single encoding. When there are no signals, pollDigest is omitted, so a miner that does not signal pays one byte for the nMinerSignals count.
