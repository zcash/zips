Terminology

The key words “MUST”, “MUST NOT”, “SHOULD”, and “SHOULD NOT” in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The terms “block chain”, “consensus rule change”, “consensus branch”, and “network upgrade” are to be interpreted as defined in ZIP 200. 2

The term “block target spacing” means the time interval between blocks targeted by the difficulty adjustment algorithm in a given consensus branch. It is normally measured in seconds. (This is also sometimes called the “target block time”, but “block target spacing” is the term used in the Zcash Protocol Specification 3.)

The term “TPS” refers to the maximum number of transactions per second supported by a Zcash subprotocol, assuming the target block spacing.

The character § is used when referring to sections of the Zcash Protocol Specification. 4

The terms “Mainnet” and “Testnet” are to be interpreted as described in § 3.12 ‘Mainnet and Testnet’. 5

Abstract

This proposal specifies a change in the block target spacing from 75 seconds to 25 seconds in NU7, and introduces per-pool action limits for the Sapling, Orchard, and Ironwood shielded pools.

This solves three problems.

  • Significantly improves the UX for actors who need 1 or 2 confirmations, such as Near Intents, and for small payments. The user-visible latency goes down 3x.
  • Increases consensus bandwidth, which would amplify the scaling impact of any future shielded pools that do not require shielded sync.
  • Introduces action limits. These provide limits on the number of actions that can go into a block. There is a global shielded budget across all shielded pools, as well as per-pool limits. These limits are configured to more than double Orchard-protocol TPS (2.9 → 6.6 TPS), while lowering the impact a DoS attacker can impose on wallets; for example, maximum shielded sync bandwidth for light clients is reduced by 37% (271 → 169 MB/day).

The action limits significantly decrease the number of Sprout and Sapling pool outputs available per block, to lower the maximum shielded sync burden under attempted DoS.

The emission schedule of mined ZEC will be the same in terms of ZEC/day, but this requires the emission per block to be adjusted to take account of the changed block target spacing.

Motivation

The motivations for decreasing the block target spacing are:

  • Reduced transaction latency. Currently, users must wait 75 seconds on average for even a single confirmation, regardless of network utilization. This creates friction for point-of-sale payments, exchange deposits, and cross-chain bridge operations. A 25-second target spacing reduces the expected wait for a first confirmation to 25 seconds on average.

  • Greater throughput. With 3× as many blocks per day and the same 2 MB block size limit, we will have allocated higher consensus bandwidth capacity. In the short term, when paired with the action limits, we will more than double the Ironwood TPS for 2-action transactions. In the longer term, when we get a shielded pool with no shielded sync burden, we will have 3x higher throughput.

The throughput goal on its own could be achieved via a block size increase. However the goal of this proposal is foremost to improve the transaction latency.

This proposal is complementary to, and does not compete with, finality mechanisms such as Crosslink 6. Faster block times improve the responsiveness of the base layer regardless of whether an additional finality gadget is also deployed. Rollback-risk analysis depends on the threat model. For models that bound an attacker by a fixed fraction of total hash power, reducing the block target spacing can reduce confirmation latency by nearly the same factor, provided that block validation and propagation times remain small relative to the target spacing. Given that is maintained here, this proposal is expected to improve confirmation latency by slightly less than 3x for users applying the same rollback-risk tolerance as today. See ‘On Slow and Fast Block Times’ 7 for analysis under several attack models.

Economic rollback models give a different result. For recipients who wait until the block rewards built on top of their payment exceed the payment value, then shorter block times significantly reduce the variance of their waiting time, while the mean stays roughly the same. Recall that proof-of-work block times have high variance, so variance reduction is a substantial benefit. This ZIP does not argue for clients reducing confirmation counts, but it does expect many users to see a lower expected time until receipt under confirmation policies comparable to those they use today.

Security

Scaling and block time reductions in Zcash impose three security costs, one on full nodes' and miners' ability to verify blocks, a second on clients for shielded sync, and a third on the whole network for the uncle rate and fork rate. Action limits are introduced in this ZIP to limit the block processing costs, and client shielded sync costs. The proposed parameterization lowers the worst case for shielded sync and node processing times relative to today, while yielding far higher Ironwood TPS. We benchmark block verification, and the uncle-rate post-proposal on networks more distributed than mainnet at maximum load is far lower than ETH-PoW was, leading to conclusion that it is safe.

Today the worst-case DoS attack can induce 271 MB of wallet sync download to clients per day, and 4.8M trial decryptions per day 8. This is achieved by fully utilizing block space with Sapling transactions that have few inputs and many outputs. The worst-case DoS for node verification time uses many Sapling inputs and a single transparent output, totaling 5,600 Sapling inputs and zero-knowledge proofs. This takes 3.2 seconds on a modern AMD laptop CPU with 4 pinned threads. Regular user flows impose far lower costs on the network than this DoS model.

We propose introducing a global shielded budget and per-pool action limits as follows:

  • A global shielded budget of 330 across all pools

  • A maximum of 330 Orchard actions per block

  • A maximum of 330 Ironwood actions per block

  • A maximum of 300 Sapling inputs + outputs. (Total inputs + outputs <= 300)

  • No Sprout JoinSplits (achieved by deploying this ZIP in conjunction with ZIP 2003 9 which disables v4 transactions).

With these limits, the worst case client load becomes 169 MB bandwidth and 2.3M trial decrypts per day. This is a 37% improvement in worst case wallet sync bandwidth despite 3× more blocks. This yields a 2.3× increase in Ironwood TPS, and keeps Sapling TPS at a higher level than today’s Ironwood TPS.

However, every wallet does have to download every compact block header, which is 90 bytes. This leads to an extra 200 kB of wallet bandwidth per day in exchange for the improved UX.

The reduced Sapling per-block limit and disabling of Sprout are justified by the current distribution of shielded funds across pools (other motivations for disabling Sprout are discussed in ZIP 2003). As of 21 October 2026, according to ZecBlock 10:

Pool Balance Share of shielded supply
Ironwood about 4,110,000 ZEC 83.0%
Sapling about 473,700 ZEC 9.6%
Orchard about 347,700 ZEC 7.0%
Sprout about 22,300 ZEC 0.4%

The vast majority of shielded funds are already in the two pools of the Orchard protocol, and most of them are in the Ironwood pool, which NU6.3 introduced 11. This trend is expected to continue. The Sapling limit is set generously relative to current usage while substantially reducing the potential for DoS. Furthermore, this ZIP is proposed to activate together with disabling v4 transactions in NU7, which would prevent any Sprout transactions from being included in blocks.

Stale block rate

The stale rate is the percentage of blocks that get orphaned, which relates to mining centralization risk, block propagation delay, and block verification times. Today the stale rate is 0.4%, but this may be lower than what pure block propagation delay may imply due to hash-power centralization in mining pools.

At 25-second block target spacing, the theoretical stale block rate is approximately 3.26%, derived from measured Zcash network propagation delays. A devnet experiment with 99 geographically-distributed Zebra nodes producing 2MB blocks at 25-second target spacing measured a stale block rate of 4.86% and a fork rate of 0.37%. Both observed figures are below the 5.4% safety threshold set by Ethereum’s historical proof-of-work stale rate. 12 The only modification required to achieve these rates was tuning TCP configuration (more details in the linked footnote). The devnet’s node distribution was significantly more decentralized than today’s mainnet, so these figures represent a near worst-case scenario. 13

Block processing time

A prerequisite for reducing the target block spacing is that block validation and propagation remain small relative to the target spacing. The per-pool action limits introduced by this proposal ensure that worst-case per-block processing time is lower than today’s. The fact that there are three times as many blocks in unit time does mean that the overall worst-case proportion of time taken for processing, and the worst cost of sync after a given time offline for full nodes will increase. We accept this trade-off. These computational limits parallelize well. At the 2,000,000-byte block size limit and 25-second target spacing, the raw block payload rate is 640 kbps, so a 10 Mbps connection has about 15 times that rate, before transport overhead.

Current worst case: A full 2 MB block today can contain up to ~617 Orchard or Ironwood actions, or ~2,107 Sapling outputs, with no per-pool limits. A fully packed Orchard-protocol block requires verifying all action proofs, spend authorization, and binding signatures, and checking validity of curve point encodings, for those ~617 actions.

Proposed worst case: With the action limits, a block contains at most 330 actions across pools. There are also separate per-pool limits:

  • 330 Orchard actions
  • 330 Ironwood actions
  • 300 Sapling inputs+outputs.

This means the new worst case block processing time, if Orchard- or Ironwood-dominant, would be 14% of today’s worst case, and Sapling’s would be less than one tenth. The worst case per-block verification work is therefore substantially reduced.

Batch verification. Ironwood transaction verification benefits from batch validation, where proof and signature verification is amortized across multiple transactions. Ironwood uses the same Action encoding and proof system as Orchard. 14 In current node software, Orchard transactions are batch-verified in groups of up to 64 transactions (each worst case being a single action). Zebra has performed batch verification during live network syncing since version 3.0.0. With the action limits, the Orchard-protocol bundles in a worst-case block can be fully batch-verified in a small number of batches.

Measured timing. We benchmarked worst-case block verification with Zebra on a modern AMD laptop CPU with 4 pinned threads.15 The figures report wall-clock time for verifying the zero-knowledge proofs and signatures in a single block, without any mempool pre-verification.

Case Block composition Mean ± stddev
Full Orchard limit (proposed) 330 Orchard actions 432.11 ± 11.03 ms
Full Sapling limit (proposed) 300 Sapling spends, 0 outputs 271.51 ± 5.03 ms
Today’s Orchard worst case ~617 actions in dense multi-action txs in a 2 MB block 769.85 ± 16.18 ms
Today’s Sapling worst case ~5,600 spends in dense multi-spend txs in a 2 MB block 3,174.90 ± 144.04 ms
  • Full Orchard limit (proposed) — binding post-NU7 verification worst case.
  • Full Sapling limit (proposed) — verification worst case is all-spends; the bandwidth worst case (all-outputs) is in Rationale.
  • Today’s Orchard worst case — dense multi-action (single-action would understate the byte bound).
  • Today’s Sapling worst case — analogous, dense multi-spend.

When transactions have already been pre-verified upon entering the mempool, block validation reduces to checking signatures and state updates, which is even cheaper. This is the typical case for a node that has been online under normal usage of the network, but under DoS attack it cannot be assumed, because the adversary can send blocks with transactions that were never in the mempool.

Privacy Implications

Reducing the target spacing does not change the information revealed by an individual shielded transaction. It does, however, change the wall-clock timing of transaction creation, inclusion, and confirmation. More frequent blocks give observers finer timing information, which may be combined with network-layer or application-layer observations. The action limits can also delay transactions under sustained demand for a particular shielded pool, making transaction timing and pool-specific congestion relevant to privacy-sensitive applications.

A fixed anchor depth measured in blocks becomes three times shorter in wall-clock time. If a wallet continues to select the final treestate three blocks behind the chain tip, the nominal distance falls from about 3.75 minutes to about 1.25 minutes. If the chain rolls back past a transaction’s anchor, the transaction becomes invalid. If it was already broadcast, its shielded nullifiers have nevertheless been revealed; a later transaction spending the same notes can then be linked to the invalidated transaction. This reliability and privacy trade-off is described in ZIP 315 16.

The stale-rate measurements in Stale block rate provide evidence about ordinary forks in the tested conditions, but do not bound the depth of a rollback caused by a consensus split, an implementation defect, an attack, or a large change in hash power. They therefore do not establish that any particular anchor depth is safe for every wallet threat model.

The shielded action limits reduce the maximum compact-block data and trial decryption work that an adversary can impose on a syncing wallet per day. They do not prevent traffic analysis or eliminate denial-of-service risk, and the per-pool limits reveal no information beyond the already-public transaction components and block composition.

This divides the per-block subsidy by an additional factor of 3 relative to the post-Blossom subsidy. As a result of this choice, the total issuance per unit of wall clock time becomes slightly lower due to rounding, which accumulates over time into a non-negligible change to the original issuance curve.

Rationale for altering the issuance curve

The choice to divide the block interval by 3 (which evenly divides the post-Blossom block interval but not the post-Blossom block subsidy) means that each block loses some fraction due to rounding relative to the original issuance curve. During the second halving period, the post-Blossom block subsidy is 1.5625 ZEC. At 25-second spacing it becomes \(\mathsf{floor}(156250000 / 3) = 52083333\) zatoshi (0.52083333 ZEC), so three post-NU7 blocks issue one zatoshi less than one pre-NU7 block. After the third halving, the subsidy is \(\mathsf{floor}(78125000 / 3) = 26041666\) zatoshi (0.26041666 ZEC), so three post-NU7 blocks issue two zatoshi less than one pre-NU7 block. Per-block this appears negligible, but over the lifetime of all issuance it can build up, so we also need to determine the total change to issued supply.

Let \(A\) be the NU7 activation height, and let \(H_3\) be the third-halving height under the 75-second schedule on the relevant network. If NU7 activates between the second and third halvings, the additional shortfall in scheduled issuance relative to keeping 75-second blocks is \(0.4872 + (H_3 - A)/10^8\) ZEC. The first term is the combined rounding shortfall from the third and later halving periods: 0.0336 ZEC from two zatoshi per 75-second interval during the third period, and 0.4536 ZEC from later periods. The second term is the one-zatoshi shortfall per remaining 75-second block in the second period. The existing 75-second schedule falls short of \(\mathsf{MAX\_MONEY}\) by 0.1848 ZEC, so the post-NU7 scheduled shortfall is \(0.6720 + (H_3 - A)/10^8\) ZEC. These figures exclude any reissuance under the Network Sustainability Mechanism specified in ZIP 237 20, which renames this \(\mathsf{BlockSubsidy}\) to \(\mathsf{ScheduledBlockSubsidy}\) and adds \(\mathsf{AdditionalBlockSubsidy}\kern-0.05em\textsf{.}\)

On Mainnet, the NU7 activation height is \(A = 3{,}543{,}405\) 18. Then \(H_3 - A = 4{,}406{,}400 - 3{,}543{,}405 = 862{,}995\kern-0.05em\textsf{.}\) The additional terminal shortfall relative to the 75-second schedule is \(0.4872 + 0.00862995 = 0.49582995\) ZEC. The total scheduled shortfall from \(\mathsf{MAX\_MONEY}\) is \(0.1848 + 0.49582995 = 0.68062995\) ZEC.

This does noticeably alter the original issuance curve, to a degree which cannot be deemed negligible. However, the parallel introduction of the Network Sustainability Mechanism 20 means that there is a pathway to re-issue these funds if desired in future.


Implications for active funding streams

Revision 3 of ZIP 214 21 extends the two funding streams to the post-NU7 third halving. At 75-second spacing, each remaining pre-halving block pays 12,500,000 and 18,750,000 zatoshi to the 8% and 12% streams. The corresponding three 25-second blocks pay \(3 \times 4{,}166{,}666\) and \(3 \times 6{,}249{,}999\) zatoshi. The streams therefore receive two and three zatoshi less, respectively, while the miner receives four zatoshi more. In this second halving period, only one fewer zatoshi is issued in total. Across the \(H_3 - A\) remaining 75-second intervals, the streams receive \(5(H_3 - A)\) zatoshi less, but total scheduled issuance falls by only \(H_3 - A\) zatoshi. This is already included in the terminal shortfall above; funding-stream rounding does not create a separate shortfall in total issuance.

Revision 2 of ZIP 207 22 extends the remaining funding-stream address period at NU7 activation, and subsequent address periods, in proportion to the change in block target spacing.

Shielded pool action limits

Define the following constants in § 5.3 ‘Constants’:

\[\mathsf{GlobalShieldedBudget} : \mathbb{N} := 330\] \[\mathsf{OrchardProtocolBlockActionLimit} : \mathbb{N} := 330\] \[\mathsf{SaplingBlockIOLimit} : \mathbb{N} := 300\] \[\mathsf{SproutBlockJoinSplitLimit} : \mathbb{N} := 0\]

In § 2 ‘Notation’, add \(\mathsf{GlobalShieldedBudget}\kern-0.05em\textsf{,}\) \(\mathsf{OrchardProtocolBlockActionLimit}\kern-0.05em\textsf{,}\) \(\mathsf{SaplingBlockIOLimit}\kern-0.05em\textsf{,}\) and \(\mathsf{SproutBlockJoinSplitLimit}\) to the list of integer constants.

In the limits below, \(\mathit{nActionsOrchard}\kern-0.05em\textsf{,}\) \(\mathit{nSpendsSapling}\kern-0.05em\textsf{,}\) \(\mathit{nOutputsSapling}\kern-0.05em\textsf{,}\) and \(\mathit{nJoinSplit}\) are the transaction fields specified in § 7.1 ‘Transaction Encoding and Consensus’ 23, and \(\mathit{nActionsIronwood}\) is the field added by ZIP 229 14. Each is taken as 0 for a transaction version that does not have the field.

For each block at height \(\mathsf{height}\) where \(\mathsf{IsNU7Activated}(\mathsf{height})\kern-0.05em\textsf{,}\) the following limits MUST be satisfied:

Per-pool limits:

  • The total number of Orchard actions across all transactions in the block MUST NOT exceed \(\mathsf{OrchardProtocolBlockActionLimit}\kern-0.05em\textsf{.}\) That is, \(\sum_{\mathit{tx} \in \mathit{block}} \mathit{nActionsOrchard}(\mathit{tx}) \leq \mathsf{OrchardProtocolBlockActionLimit}\kern-0.05em\textsf{.}\)

  • The total number of Ironwood actions across all transactions in the block MUST NOT exceed \(\mathsf{OrchardProtocolBlockActionLimit}\kern-0.05em\textsf{.}\) That is, \(\sum_{\mathit{tx} \in \mathit{block}} \mathit{nActionsIronwood}(\mathit{tx}) \leq \mathsf{OrchardProtocolBlockActionLimit}\kern-0.05em\textsf{.}\)

  • The total number of Sapling inputs and outputs across all transactions in the block MUST NOT exceed \(\mathsf{SaplingBlockIOLimit}\kern-0.05em\textsf{.}\) That is, \(\sum_{\mathit{tx} \in \mathit{block}} (\mathit{nSpendsSapling}(\mathit{tx}) + \mathit{nOutputsSapling}(\mathit{tx})) \leq \mathsf{SaplingBlockIOLimit}\kern-0.05em\textsf{.}\)

  • The total number of Sprout JoinSplits across all transactions in the block MUST NOT exceed \(\mathsf{SproutBlockJoinSplitLimit}\kern-0.05em\textsf{.}\) That is, \(\sum_{\mathit{tx} \in \mathit{block}} \mathit{nJoinSplit}(\mathit{tx}) \leq \mathsf{SproutBlockJoinSplitLimit}\kern-0.05em\textsf{.}\)

Global shielded budget:

In addition to the per-pool limits, the total shielded cost across all pools in a block MUST NOT exceed \(\mathsf{GlobalShieldedBudget}\kern-0.05em\textsf{,}\) where the shielded cost of a block is defined as:

\[\sum_{\mathit{tx}} \left(\mathit{nActionsOrchard}(\mathit{tx}) + \mathit{nActionsIronwood}(\mathit{tx})\right) \;+\; \sum_{\mathit{tx}} (\mathit{nSpendsSapling}(\mathit{tx}) + \mathit{nOutputsSapling}(\mathit{tx})) \;+\; 2 \times \sum_{\mathit{tx}} \mathit{nJoinSplit}(\mathit{tx})\]

Thus, Orchard and Ironwood do not receive separate 330-unit global budgets: every action in either pool consumes one unit of the same global budget.

The factor of 2 for Sprout JoinSplits reflects that each JoinSplit produces 2 shielded outputs. While \(\mathsf{SproutBlockJoinSplitLimit} = 0\kern-0.05em\textsf{,}\) this term is always zero.

This global budget ensures that the worst-case shielded sync bandwidth per block is bounded regardless of which combination of pools is used.

These limits do not apply to the transparent components of transactions. The overall 2 MB block size limit continues to apply as before.

Rationale: Compact sync bandwidth per action

The limits above are chosen to bound the worst-case bandwidth that lightweight wallets must download for shielded sync. The Light Wallet Protocol represents both Orchard and Ironwood actions using CompactOrchardAction. 24 The per-action field payload has the following costs:

Orchard and Ironwood: 148 bytes per action, consisting of:

Field Size
cmx (note commitment) 32 bytes
nullifier 32 bytes
ephemeral public key 32 bytes
truncated note plaintext 52 bytes
Total 148 bytes

Sapling: 32 bytes per spend (input) and 116 bytes per output, consisting of:

Field Size
Per spend: nullifier 32 bytes
Per output: cmu (note commitment) 32 bytes
Per output: ephemeral public key 32 bytes
Per output: truncated note plaintext 52 bytes
Per spend total 32 bytes
Per output total 116 bytes

With these limits, the worst-case compact sync bandwidth per block is:

  • Orchard or Ironwood: \(330 \times 148 = 48{,}840\) bytes
  • Sapling: at most \(300 \times 116 = 34{,}800\) bytes (all-output pathological case)

Due to the global shielded budget, these cannot stack: a block that uses 330 Orchard and/or Ironwood actions has zero budget remaining for Sapling. The worst-case compact sync bandwidth per block is therefore always bounded by the Orchard-protocol case at 48,840 bytes.

See the Rationale section for the full daily bandwidth analysis.


Effect on difficulty adjustment

As with the Blossom activation 25, the difficulty adjustment parameter \(\mathsf{PoWMedianBlockSpan}\) refers to a number of blocks and does not change at activation. The change in the effective value of \(\mathsf{PoWTargetSpacing}\) will cause the block spacing to adjust to the new target at the normal rate for a difficulty adjustment. See Difficulty averaging window in the Rationale for analysis of the \(\mathsf{PoWAveragingWindow}\) change.

It is likely that the difficulty adjustment for the first few blocks after activation will be limited by \(\mathsf{PoWMaxAdjustDown}\kern-0.05em\textsf{.}\) This is not anticipated to cause any problem.

Minimum difficulty blocks on Testnet

On Testnet, the minimum-difficulty block threshold defined in ZIP 205 26 and modified by ZIP 208 25 is changed at the Testnet NU7 activation height. For a block at height \(\mathsf{height} \geq 299188\kern-0.05em\textsf{,}\) the threshold is \(6 \cdot \mathsf{PoWTargetSpacing}(\mathsf{height})\) seconds before NU7 activation and \(18 \cdot \mathsf{PoWTargetSpacing}(\mathsf{height})\) seconds from NU7 activation onward. The latter is \(18 \times 25 = 450\) seconds. A block is a minimum-difficulty block only if its block time is strictly greater than this threshold after the preceding block’s time. Thus, at and after Testnet NU7 activation, a gap of 450 seconds does not qualify, while a gap of 451 seconds does. In that case, the block’s nBits field MUST be set to \(\mathsf{ToCompact}(\mathsf{PoWLimit})\) as specified by ZIP 208. This change does not affect Mainnet.

Default expiry delta

The default expiry delta of 40 blocks (approximately 50 minutes at 75-second spacing) is tripled from NU7 activation, to keep that expiry time. In “Expiration height” 27, replace:

40 blocks from the current height, as specified in [#zip-0203]_.

with:

A wallet SHOULD create transactions using a default expiration height of
40 blocks after the target height (the height of the next block after the
chain tip) before NU7 activation, and of 120 blocks after the target height
from NU7 activation, as specified in [#zip-0203]_ and [#zip-0218]_. If the
user has configured an expiry delta, the configured value SHOULD be used both
before and after NU7 activation.

In “References” 16, add:

Anchor selection depth

ZIP 315 16, recommends selecting an anchor 3 blocks back from the chain tip when constructing shielded transactions. The recommended anchor depth SHOULD remain at 3 blocks after activation, reducing the average wall-clock anchor delay from ~3.75 minutes to ~1.25 minutes.

Transactions exceeding a block limit

A transaction that would by itself violate any of the per-pool limits or the global shielded budget specified above cannot be included in any block at a height where NU7 is active. For example, a transaction with 200 Orchard actions and 200 Ironwood actions satisfies both per-pool limits but exceeds \(\mathsf{GlobalShieldedBudget}\kern-0.05em\textsf{.}\)

Nodes SHOULD NOT admit such a transaction to their mempool, or relay it, if NU7 is active at the height of the candidate next block. Wallets SHOULD NOT create such a transaction for a target height at or after NU7 activation.

Rationale

Rationale for block-count-based constants

The constant COINBASE_MATURITY is listed for completeness. Its value is fixed by a consensus rule in § 7.1.2 ‘Transaction Consensus Rules’ 28, which this ZIP does not change.

The constant NETWORK_UPGRADE_PEER_PREFERENCE_BLOCK_PERIOD represents a duration, but is deliberately not scaled, as with Blossom 25. Its window therefore shrinks from 1.5 days at 75-second spacing to 12 hours at 25-second spacing.

This proposal is fundamentally about decreasing the target spacing, which makes the wall-clock margin shorter for any given MAX_REORG_LENGTH. Zebra’s MAX_REORG_LENGTH was previously 99, set just below COINBASE_MATURITY (= 100) by Bitcoin-inherited convention. At Zcash’s launch 150-second spacing it covered about 4.2 hours, at the current 75-second spacing about 125 minutes, and at NU7’s proposed 25-second spacing only about 42 minutes.

Recent incidents show consensus splits can persist beyond tens of minutes: for example, Litecoin’s April 2026 MWEB incident produced a 13-block invalid chain that was later reorged out, with a ~3-hour recovery window per the postmortem 29. The optimal long-term value for MAX_REORG_LENGTH likely needs to change further in the future, but that is out of scope here. Raising it to at least 600 blocks restores the ~4.2-hour wall-clock window it provided at Zcash’s launch 150-second target spacing, while COINBASE_MATURITY remains 100. This is more conservative than the ~125-minute window at today’s 75-second spacing. Given the incident above and that the launch 150-second-spacing value predates this line of evidence, restoring the launch wall-clock margin is the safer choice.

This deliberately means that a supported reorg may invalidate a mature coinbase output. That case is already a valid consequence of deep PoW reorgs in the abstract protocol model.

Since version 5.2.0, Zebra keeps a rollback window of 1000 blocks before and after activation (about 20.8 hours at 75-second spacing and 6.9 hours at 25-second spacing), which satisfies the floor of 600.

Rationale for anchor selection depth

This follows the same precedent set by the Blossom upgrade (ZIP 208 25), which did not update the anchor depth and therefore halved delay.

Parameter Current Post–activation Notes
Recommended anchor depth 3 blocks (~3.75 min) 3 blocks (~1.25 min) No change; follows Blossom precedent

The increased likelihood of forking due to block time reduction should not be concerning here. For an issue to occur when anchor depth is 3 blocks back, you must have a 4 block re-org. In the many years of Ethereum PoW, a 4 block re-org has never been observed 30. So we are not practically at risk of inherent randomness causing a re-org. In other POW chains, re-orgs of 4+ blocks resulted from a consensus split of some form, including the recent Litecoin attack, or an attack from a surge in hashpower. Anchor height depth is not intended to protect against those two vectors.

Shielded sync bandwidth analysis

The per-pool block space limits are chosen so that the worst-case daily bandwidth for lightweight wallet syncing does not increase relative to the current protocol. This section presents the analysis.

The pre-activation Sapling estimates use the Shielded Sync Simulator’s 8 one-spend, 64-output transaction model; IOs count both spends and outputs. They are not maxima over arbitrary input/output mixes. The simulator uses 32 compact bytes per spend and 112 per output, whereas the post-activation Sapling bound above uses 116 bytes per output.

The worst-case compact sync bandwidth is 169.10 MB/day, a reduction of 37% from today’s worst case of approximately 270.5 MB/day. This is despite a 3× increase in block frequency and overall throughput capacity.

The binding constraint is Orchard or Ironwood at 330 actions per block: \(330 \times 148 \times 3{,}456 + 90 \times 3{,}456 = 169.10\textsf{ MB/day}\kern-0.05em\textsf{.}\)

The trial decryption count also decreases significantly, since the per-block action limits more than offset the 3× increase in block count.

Note that the trial decrypt count per account is 2× the number of shielded outputs/actions, because wallets must attempt decryption with both the internal and external incoming viewing keys (IVKs). The internal IVK detects change outputs sent back to the wallet, while the external IVK detects incoming payments. In principle, wallets could avoid trial decrypts with one of their IVKs assuming other sync trade-offs are taken, but current Sapling and Orchard-protocol wallets always attempt both.

Normal transaction throughput

For standard 2-action Orchard or Ironwood transactions, the action limit of 330 allows \(\lfloor 330 / 2 \rfloor = 165\) transactions per block, giving:

\[\mathsf{orchard\_protocol\_tps} = 165 \;/\; 25 = 6.6 \textsf{ TPS}\]

For comparison, the current protocol (75s blocks, block-size limited) supports approximately 2.9 TPS for 2-action Orchard transactions. This is a 2.3× increase in normal Orchard throughput.

Sapling throughput. For standard Sapling transactions (2 spends + 2 outputs = 4 IOs), the limit of 300 IOs allows \(\lfloor 300 / 4 \rfloor = 75\) transactions per block, giving \(75 / 25 = 3.0\) TPS. Even with the reduced Sapling limit, the post-NU7 Sapling TPS (3.0) still exceeds the current pre-NU7 Orchard TPS (2.9).

Fee incentives and DoS resistance

A concern with per-pool limits is that a DoS attacker could fill one pool’s budget to crowd out transactions in another pool. The global shielded budget prevents this from being worse than filling any single pool, but it is worth examining whether fee incentives create an asymmetry.

Under ZIP 317 31, the conventional fee is based on logical actions. Each Orchard or Ironwood action counts as one logical action, but a transaction’s Sapling spends and outputs count as \(\max(\mathit{nSpendsSapling}, \mathit{nOutputsSapling})\) logical actions, whereas they consume \(\mathit{nSpendsSapling} + \mathit{nOutputsSapling}\) units of the global shielded budget. A balanced Sapling bundle therefore buys budget units at half the Orchard or Ironwood price, while an all-output or all-spend Sapling bundle pays the same price per unit.

Furthermore, because the global shielded budget is shared, filling one pool’s budget necessarily reduces the remaining budget for all other pools by the same amount. An attacker who spends their entire budget on Sapling spam at 300 IOs leaves only 30 Orchard or Ironwood actions available in that block. With 150 Sapling spends and 150 Sapling outputs, plus 30 Orchard actions, the attacker exhausts the budget for 180 logical actions, about 55% of the conventional fee for 330 Orchard or Ironwood actions. Such a block carries less compact sync data, however: \(150 \times 32 + 150 \times 116 + 30 \times 148 = 26{,}640\) bytes, against \(330 \times 148 = 48{,}840\) bytes. The global budget ensures that the total shielded sync cost per block is bounded to 330 units regardless of the attacker’s pool choice.

The bounds this ZIP sets therefore still hold: a block contains at most 330 units in any mix of pools, and the cheapest way to exhaust the budget carries less compact sync data than an Orchard-protocol block. What the Sapling pricing changes is the cost of crowding other transactions out of a block. At the ZIP 317 marginal fee of 5,000 zatoshis, it is 0.009 ZEC per block, about 31 ZEC per day at 25-second spacing, instead of 0.0165 ZEC and about 57 ZEC. A future ZIP could remove the difference by counting \(\mathit{nSpendsSapling} + \mathit{nOutputsSapling}\) logical actions in ZIP 317, which raises the conventional fee of a typical one-spend, two-output Sapling transaction by half, or by having block templates rank transactions by fee per unit of shielded budget rather than per logical action.

The 330-action per-pool cap also allows either Orchard or Ironwood transactions to use the full global budget when other shielded pools are not used.

Difficulty averaging window

This proposal increases \(\mathsf{PoWAveragingWindow}\) from 17 to 102 at NU7 activation (specified in Averaging window under Consensus changes), so that the wall-clock smoothing window is \(102 \times 25 = 17 \times 150 = 2{,}550\) seconds — the same wall-clock window the value \(\mathsf{PoWAveragingWindow} = 17\) was originally chosen to provide at Zcash’s launch target spacing of 150 s. At today’s 75 s spacing the same value covers only 1,275 s, and at NU7’s proposed 25 s spacing it would cover only 425 s.

The motivations are:

  1. To preserve the wall-clock duration over which difficulty is smoothed, so that NU7 does not amplify difficulty-manipulation attacks like the one recently observed on Litecoin 29.
  2. As an additional improvement over keeping \(\mathsf{PoWAveragingWindow} = 17\kern-0.05em\textsf{,}\) to reduce the standard deviation of block-spacing averages over short rolling windows.

Under a Zebra difficulty-adjustment simulator 32 with a stable hash rate and with \(\mathsf{PoWAveragingWindow} = 17\) unchanged across the transition, the expected block spacing recovers to within 5% of the new 25 s target within 62 blocks of NU7 activation:

Expected spacing Blocks after activation Wall–clock
75 s (pre-NU7 target) — —
56.8 s (activation) 0 —
\(\leq 30\) s 30 ~21 min
\(\leq 26.25\) s 62 ~36 min

Setting \(\mathsf{PoWAveragingWindow} = 102\) is expected to require roughly 6× as many blocks to cross each threshold, which is the same wall-clock duration as recovery would have taken at Zcash’s launch 150 s spacing with \(\mathsf{PoWAveragingWindow} = 17\kern-0.05em\textsf{.}\)

For a real-world reference point, the Blossom upgrade 25 made a 2× target-spacing reduction (150 s → 75 s) with \(\mathsf{PoWAveragingWindow}\) unchanged; mainnet block spacing (20-block rolling average) reached approximately 74 s at height 653,664 — 64 blocks after activation.

Two geographically-distributed devnets of 99 Zebra nodes across 14 regions (1 vCPU per node), one at \(\mathsf{PoWAveragingWindow} = 17\) and one at 51, confirmed a ~1-second reduction in the standard deviation of 5- and 10-block rolling-average block spacings. The variance reduction is expected to be somewhat larger at \(\mathsf{PoWAveragingWindow} = 102\kern-0.05em\textsf{.}\)
